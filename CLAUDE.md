# Геймификация для ВСМ

Обучающее приложение-симулятор для проводников высокоскоростных магистралей (ВСМ).
Проект для трека «Геймификация для ВСМ» на Хакатоне Московского транспорта - https://mt-hackathon.ru/

## ✅ Трактовка кейса определена (ТЗ от 25.09.2026)

Расхождение между Положением и сайтом снято официальным ТЗ с открытия хакатона:
**делаем обучающий тренажёр для проводников.** Пассажирская игра с программой

Оставленная в модели нейтральность (`audience`, декларативные `metrics`, `tracks`)

## Проблематика (из ТЗ - формулировки заказчика)

Использовать дословно в питче, это язык, на котором говорит жюри:

- недостаточная эффективность классических форм обучения (лекций, тестов) для формирования
  навыков работы **в условиях стресса и дефицита времени**;
- отсутствие **безопасной среды** для отработки нештатных ситуаций без риска для реальных пассажиров;
- сложность **объективной оценки гибких навыков** (soft skills) проводников;
- низкая **мотивация** сотрудников к постоянному профессиональному развитию.

Контекст объекта: ВСМ Москва - Санкт-Петербург, ~700 км, первая высокоскоростная
магистраль в России, проходит через Москву, Московскую, Тверскую, Новгородскую,
Ленинградскую области и Санкт-Петербург.

## Образ решения (из ТЗ)

Модульное приложение из трёх частей:
- **Frontend** - веб-интерфейс или мобильное приложение для проводника → наш выбор: **PWA**
- **Backend** - сервер бизнес-логики: движок сценариев, начисление очков компетенций
- **Storage** - БД сотрудников, сценариев, их активности и достижений

> **Решение должно предоставлять API для интеграции с внутренними HR-системами
> и системами обучения ВСМ.** - выделено в ТЗ отдельным блоком, то есть это не пожелание.

## Контекст задачи

ВСМ - премиальный уровень сервиса, скорость до 400 км/ч. Проводник обязан принимать решения
за секунды: конфликты пассажиров, медицинские инциденты, нештатные ситуации. Классические
тесты и лекции не готовят к реальному стрессу и не развивают гибкие навыки.

Цель - виртуальная среда, где сотрудник проходит сложные рабочие сценарии, принимает решения
с учётом таймера, видит последствия своих действий и зарабатывает очки компетенций.

## Обязательная функциональность (из ТЗ кейса)

- **Движок сценариев** - нелинейные диалоги, игровые ситуации с несколькими вариантами развития событий
- **Игровые механики** - таймеры на принятие критических решений, шкала «лояльность пассажира», «рейтинг безопасности»
- **Геймификация обучения** - профиль сотрудника, система достижений (ачивок), таблица лидеров среди проводников

## Платформа

**Mobile-first** (web и/или native). Все интерфейсные решения проектируются от мобильного
экрана: вертикальная компоновка, тач-цели, читаемость на ходу. Десктоп - вторичен.

## Архитектура

Подробное описание - `docs/architecture.md` (это же сдаваемый документ № 1).

**Стиль: модульный монолит на бэкенде, раздельный фронтенд.** Один процесс NestJS
с модулями за жёсткими границами, отдельно собираемая и деплоимая PWA, один Postgres.
Микросервисы для такого масштаба избыточны - это сознательный выбор, так и говорить жюри.

Монорепо на pnpm workspaces. Реальный состав команды - **2 разработчика** плюс двое
на контент, визуал и презентацию; план рассчитан на них, а не на пятерых.

```
apps/
  pwa         Vite + React - PWA проводника, offline-first, mobile-first;
              страница методолога - внутри, под ролью
  api         NestJS - REST + OpenAPI + SSE + webhook для HR/LMS
packages/
  scenario-engine   чистый TS - интерпретатор графа + линтер
  ui                дизайн-система (shadcn/ui + Tailwind)
```

Стек MVP: Node 22 LTS, pnpm, TypeScript, NestJS, PostgreSQL 16, Vitest на движке,
Docker Compose, nginx. ORM и слой контрактов - те, что разработчики уже знают
(по умолчанию Prisma и `@nestjs/swagger`); новый инструмент в первый день хакатона -
минус три часа. Без Redis, Turborepo, Playwright, Web Push, OIDC, React Flow -
всё это целевая архитектура, задокументированные точки расширения.

**Скоринг - модуль `api/src/scoring` с интерфейсом `ScoringQueue`.** В MVP исполняется
синхронно, в проде - отдельный воркер; переключается конфигом, код домена не меняется.

**Подход к разработке - тонкий срез насквозь.** К вечеру 25.09 одно прохождение работает
end-to-end; всё остальное наращивается на живой каркас. Слои параллельно с интеграцией
в последний вечер - путь к сломанному демо.

**Офлайн-очередь - своя, в IndexedDB**, отправка по `online` и при открытии.
Background Sync API не поддерживается Safari - на iPhone он не работает.

Почему PWA, а не Next.js или native: отдельный API и офлайн-режим делают SSR ненужным,
Capacitor требует статический билд, а публичные сторы для корпоративного приложения -
лишняя внешняя зависимость. Vite даёт лёгкий бандл и чистый static export.

### Ключевые принципы

1. **Сценарий - это данные, а не код.** Граф узлов в JSON, интерпретируемый движком.
   Контент добавляется без релиза.
2. **Движок изоморфен.** `packages/scenario-engine` импортируется и клиентом
   (проигрывание), и воркером (пересчёт очков) - одна логика, ноль расхождений.
3. **Клиент не считает очки.** Клиент отправляет лог решений, сервер пересчитывает
   тем же движком. Лидерборд не накручивается.
4. **Контракт раньше реализации.** `packages/contracts` пишется первым, фронт работает
   против mock-сервера и не ждёт бэкенд.
5. **Сценарии версионируются.** Попытка ссылается на конкретную опубликованную версию -
   правка контента не ломает историю прохождений.
6. **Офлайн - не опция, а норма.** Проводник в поезде. Сценарий проигрывается полностью
   на устройстве, результат уходит при появлении связи через Background Sync.
7. **Интеграция - часть продукта, а не приложение к нему.** API для HR и LMS выделено
   в ТЗ отдельным блоком: webhooks, xAPI-события, выгрузки, OIDC.

### Платформа доставки

PWA + Capacitor для APK. Одна кодовая база - веб по ссылке, установка на домашний экран,
APK в RuStore. Независимость от Google Play и App Store - осознанное решение: для
корпоративного приложения транспортной организации публичные сторы это лишняя внешняя
зависимость, которой можно не иметь.

Self-hosted инфраструктура (MinIO вместо S3, свой Postgres, свой TLS) - прямой ответ на
152-ФЗ: персональные данные сотрудников не покидают контур заказчика. В питче проговорить.
